# 桌面安装后验收清单

本清单只列**必须在安装后的桌面应用里人工执行**的检查。静态预览、浏览器构建、
`vite build`、单元测试与 `cargo check` 都不能替代这些步骤；只跑静态检查就把个人版称为
“已验收”属于虚假通过。

记录方式：逐项填写“实际结果”和“取证位置”。任何一项未执行就写“未运行”，不得写“通过”。
截图、窗口标题、错误码原文与日志路径都可作为取证；没有取证的结果不计入通过。

Windows 11 x64 本次交付将干净原生安装/卸载、实际桌面IPC和人工操作分开记录。自动化真实IPC可以证明指定交互；未执行的系统选择器、托盘人工操作和显示器/DPI检查仍写未运行，不借旧版本或浏览器mock补成通过。

## 0 记录头

| 字段 | 值 |
| --- | --- |
| 安装包版本 | 从安装文件名与 `bundle` 版本读取，逐字记录 |
| 安装包 SHA256 | 记录 `.exe` 的完整摘要 |
| 安装模式 | 应与 `tauri.conf.json` 的 `windows.nsis.installMode` 一致（当前为 `currentUser`） |
| 安装器语言 | 应与 `languages` 一致（当前为 `SimpChinese`、`English`） |
| 操作系统版本 | Windows 版本与构建号 |
| 显示器与缩放 | 单/多显示器、DPI 缩放比例 |
| Obsidian 版本 | 库操作相关任务才需要；本清单不比对 Obsidian |
| 执行人 / 日期 | 真实姓名与本地日期 |
| 安装包签名状态 | 是否代码签名；未签名要写明，不写“已验证签名” |

完整安装资源包括同目录 CLI、`pdf-python/` 完整锁定环境和许可、根目录 VC 运行库、`helpers/` 模型程序、`fixtures/` 作者样例及冻结账本、`samples/` PDF和中文快速开始。用安装目录中的 `payload-manifest.json` 逐字节核对；缺失资源不能借开发仓库、PATH或已装 Python 补齐后称作安装通过。

## 4A 资料与模型笔记

本节覆盖 B15 新接入的流程。原生自动化可以保存真实安装版 IPC 与 UI 操作证据，但不替代未执行的人工条目。真实模型检查只有使用本机当前加密凭据并实际调用时才计入；离线样例与 local_http_test 明确单列。

| 编号 | 操作 | 期望 | 实际结果 | 取证 |
| --- | --- | --- | --- | --- |
| 4A.1 | 明确选择一份中文空格路径的文本 PDF 并导入 | 保存真实原件与解析报告，显示实际状态及真实物理页区域；无独立安装 Python 的要求 | | |
| 4A.2 | 导入扫描页和损坏 PDF | 扫描页显示需要复核且不伪造正文；损坏文件显示失败及稳定错误码 | | |
| 4A.3 | 选择已确认文本区域并查看待发送原文 | 原文与保存资源的 UTF-8 范围一致；最多64单位且正文最多64KiB，超过时请求前拒绝 | | |
| 4A.4 | 在未配置凭据时尝试模型整理 | 显示模型设置入口；密钥通过系统遮蔽输入框加密保存，不进入前端或原始记录 | | |
| 4A.5 | 在缺失共享用量账本时查看模型设置 | 用量显示未知；恢复需明确确认没有未记录的新调用，沿用33,185已用与10条历史，不能自动归零 | | |
| 4A.6 | 主动点击一次模型整理，再连续点击及取消 | 同一操作最多一次请求；取消与失败保留实际结果，未知用量继续占用预算，不自动重试 | | |
| 4A.7 | 把已成功模型结果导出到新的中文空格测试目录 | vault/ 内为可读概念与证据笔记和真实原件，reports/ 保留审计；明确 pending/unverified，条件、单位和页码定位保留 | | |
| 4A.8 | 对已存在目录及已有 Vault 内子目录导出 | 请求前拒绝，原有内容不改变；不接管用户生产 Vault | | |
| 4A.9 | 重启后选择同一项目和已保存成功结果导出 | 重新核对来源与结果，无额外模型请求；篡改结果或来源后拒绝 | | |
| 4A.10 | 运行离线安装自检 | 明确作者样例、0模型调用，在独立新测试根生成样例笔记，不混入自己的 PDF 流程 | | |

## 8 明确不属于本清单的检查

- 科学正确率、知识召回率、200 原子金标准：属于内容质量门槛，不是安装验收。
- 正式审批、科学核验与生产 Vault 发布：B15 的候选预览始终是待核验的新测试 Vault，不构成这些能力的验收。
- 通用 OCR、千页/万原子规模、24 小时连续运行、3000 笔记/200 人工改动：属于规模与稳定性门槛。
- Obsidian 版本兼容矩阵：见 `doc/technical/VISUAL_COMPATIBILITY.md`。

## 9 判定规则

全部项目都必须在安装后的应用中实际执行并留下取证，才能写“个人版安装验收通过”。
任何一项未运行就只能写“部分通过”，并逐项列出未运行项。静态检查（配置审计、构建、
单元测试）单独列在验证记录的“可自动执行部分”，不与本清单混算。
