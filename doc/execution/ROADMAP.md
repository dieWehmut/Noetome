# 分阶段开发路线

本计划追求每轮有小成果且不破坏已验证能力。它把 [PRD里程碑](../requirements/PRD.md) 拆成可滚动细化的批次，不一次展开全产品任务树。

## 执行节奏

- 一次普通开发请求默认完成一个近期任务；可以包含必要的实现、测试、修复和提交子步骤。
- 同时最多一个任务进行中。可并行做同任务内的独立审查或实现，不能让多个代理各自启动下一阶段。
- 一个批次最多3个详细任务。当前批次全部验收后，根据实际结果展开下一批，不提前锁死远期接口。
- 用户明确要求连续推进时，可顺序执行多个任务；每个任务仍独立验收、记录、提交，不能跳过失败点。
- 不用固定小时数承诺进度。任务一旦需要多个独立能力或大量跨模块修改，先拆成更小任务卡。

## 每个阶段的继续条件

1. 当前任务卡中的验收和必要回归都已实际运行；失败已修复或如实标为阻塞。
2. 开发日志与文件产物一致，未把计划、fake、跳过测试或未运行工具算作完成。
3. 新增Schema、接口或用户行为已更新对应标准，不靠聊天历史维护隐性决定。
4. 工作形成明确提交，工作区没有不明改动；检查完成后推送当前分支。
5. 下一步基于实际剩余问题选择；若存在影响正确性或数据安全的回归，先修复，不叠加功能。

在真实PDF与API阶段逐步建立正式基准资料包，最终仍需通过PRD规定的质量、人工保护和长任务门槛。早期小批次验收不能替代个人可用版的完整验收。
