## 关键取舍

1. **桌面层只投影，不派生**。`tasks::read` 分别调用 `fixture_run::status`、`research_store::list`、
   `retrieval_store::list`、`revision_store::list`，四个入口本身以只读方式打开账本
   （`Journal::open(root,false)`、`open_readonly`/`open_mode(root,false)`）。计数、状态、错误码全部
   来自返回的 JSON；前端不重算、不转百分比、不补全缺失字段。原始 JSON 通过 `record` 字段整份返回，
   页面可按需展开对照。
2. **四态区分，不把失败当空任务**。`present`（已读取）、`absent`（尚未建立，仅当路径不存在时）、
   `failed`（六单元运行自报失败）、`unreadable`（读取被 CLI 拒绝）。`absent` 只调用
   `path.exists()` 判断，不打开账本；`unreadable` 保留 CLI 原错误码与原 `代码：说明` 文本。
3. **四维状态用确定性规则**，与主任务分开：`count_state(completed,total)` 在分母为零时给
   `not_applicable`、全完成时 `complete`、否则 `incomplete`；`quality_validation` 恒为 `not_run`
   并写明原因；`optional_research` 在六单元运行中恒为 `not_requested`，在有界检索中按是否已记录
   终止理由给 `incomplete`/`complete`；运行尚未产生编译报告时 `knowledge_compilation` 给
   `not_started` 而不是 `complete`。
4. **不新增写路径**。桌面层没有任何写命令；测试用读取前后字节快照证明零写入。`capabilities/main.json`
   未改动（没有引入文件/网络插件权限），所有读取经 Tauri 命令进入 Rust。
5. **`capabilities` 与真实能力同步**。`RuntimeInfo.capabilities` 由四项扩为五项，运行检查页会如实
   显示 `task.read`；`cli_preview` 仍只接受 `help`/`version`。

## 单测覆盖（成功/缺失/损坏三类 + 零写入）

`crates/noetome-desktop/src/tasks.rs` 的 10 项测试，全部在 `target/desktop-task-tests` 下自建唯一目录，
`sandbox()` 返回 `canonicalize()` 后的路径（否则含 `..` 的路径会被 CLI 判成 `PROJECT_UNSAFE_PATH`），
用相对路径→字节的 `snapshot()` 断言「没写任何字节」：

| 测试 | 覆盖 |
| --- | --- |
| `unknown_kind_and_empty_path_are_refused_by_name` | 未知 kind 与空路径分别返回 `DESKTOP_TASK_KIND`/`DESKTOP_TASK_PATH`，且不读目录 |
| `missing_root_is_reported_as_not_established_not_as_a_failure` | 四类 kind 对不存在的根全部返回 `absent`，不是失败 |
| `four_kinds_are_read_without_writing_anything` | 四类根读取前后快照完全相等；`state=present`；四维数量恒为 4 |
| `values_are_copied_from_the_ledger_instead_of_being_derived` | 运行 ID 与 `record["run_id"]` 一致；不伪造不存在的字段；四维分别为 incomplete/not_started/not_run/not_requested |

| `a_foreign_or_corrupt_root_keeps_the_cli_code_and_is_never_written` | 空目录 → `RESEARCH_UNKNOWN_ROOT` 且含「未修改任何文件」；破坏 sqlite 头 → `PROJECT_INVALID_DATABASE`；两次快照均不变 |

## 仍未闭合

1. **Windows 原生安装内的桌面交互未运行**：本环境是 Linux/WSL，没有运行 NSIS 安装包，也没有在
   安装后的应用里点过任务类型切换、「选择目录」与「读取任务状态」，因而 IPC 的端到端可用性
   只在单测与构建层面被证明。

   从桌面发起运行/检索/修订属于后续任务的范围。
3. **完整 `cargo test --workspace` 有环境既有失败**（见上表），本任务未修复它们，也不宣称全部通过。
4. **未接审批、发布与研究候选决策界面**：任务中心只读；接受/拒绝候选、发布与回滚仍未接入桌面。
5. **四维状态规则是桌面侧的确定性映射**，与编译报告的同名维度同义但独立实现；
   两者若将来不一致，需要在契约文档里再对齐（当前两处都不做百分比）。
6. **静态构建与浏览器预览不能替代安装后验收**：`vite build` 通过只证明前端可编译。
