关键实现取舍（引自契约并已实际体现）：

- 托管根只允许 `control/{owner.json,vault.sqlite,update.lock}`、`baseline/`、`vault/`、`releases/<release_id>/`；`status` 全程只读。
- `approve` 绑定四样：计划正文 SHA256、受影响路径的现场 FileStamp、影响清单规范序列化、owner/metadata 指纹。`approve` 不写 `vault/`。
- `publish` 顺序为：先绑 owner/metadata 指纹（不符即 `approval-stale`）→ 取锁 → 查账本（同一批准且已 published 时幂等返回、不写字节）→ 才核现场指纹（只核仍 pending 的路径）。指纹核若排在幂等短路之前，合法重放会永远 stale。
- `publish` commit 段先写 pending 记录再逐项落盘，每项写回账本并追加 `commit.log`；进程在 pending 后被杀，`status` 报 `needs_recovery`，同一批准可续跑。
- `rollback` 只生成反向计划文件；发布后被人改过的路径以 `rollback-conflict` 停止且不写任何字节。

## 仍未闭合

1. **Windows 原生门禁未运行**：本卡的全部执行都在 Linux（WSL2 Ubuntu-22.04）上完成。Windows 的 fmt/check/test、`vault` 行为、SIGKILL 恢复、PowerShell 相关套件均未在本卡执行；T02 的跨平台边界结论不能替代本卡。
2. **两项时间敏感失败未消除**：`--test compile` 的 `windows_path_controls...` 与 lib 的 `extraction_api_transport::timeout_and_cancel...` 是既有红/时序抖动，已在基线复核，本卡未修复（不属于本卡范围）。
3. **不宣称的能力**：本卡不接管生产 Vault，不宣称完整桌面（Tauri）审批界面、规模（大 Vault/多笔记）表现、科学质量或任意断电点的原子性；`needs_recovery` 恢复覆盖的是「pending 已落账、逐项未写完」这一真实终止边界，不是任意时刻断电的完备证明。
4. **`vault` 只对冻结包的形状做了验证**：两篇笔记 + 一个 PNG + 一条链接 + 五种操作的作者包是唯一实测形状；更大或更复杂的托管集合未测。
